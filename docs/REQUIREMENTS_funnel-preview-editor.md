# 要件定義: 申込画面のプレビュー & 文言編集（管理画面）

作成: 2026-08-04 / ステータス: **確定**（2026-08-04 ユーザー確認済み）

**確定した設計判断**:
1. 編集範囲: web申込ファネル + **LINE側の文言も第1弾に含める**（§5b）
2. 公開フロー: 下書き→公開の2段階
3. 権限: admin のみ

---

## 1. 背景・目的

エンドユーザーが契約時に見る画面（メイト選択 → プラン選択 → 完了）は、運営が日常的に
「今どう見えているか」を確認し、文言を磨き、メイト写真の変更結果を確かめたい画面である。
現状はそのどれもできない:

- **文言はすべてソースコードにハードコード**（6ファイルに約60文字列）。変更のたびに開発者が必要
- **確認手段が本番URLを自分で開くだけ**。スマホでの見え方・写真変更の反映は勘で判断している
- 管理画面には価格・写真・プロフィールの編集はあるが、**「ユーザーに見えている画面」を見る場所がない**

この機能は「引き渡して自走させる」の一環。運営が開発者なしで
**見る → 直す → 確かめる** を1画面で完結できるようにする。

## 2. 画面の目的・主ユーザー・最重要アクション

| 項目 | 内容 |
|---|---|
| 画面の目的 | 申込ファネルの実際の見え方を確認し、文言をその場で直し、反映を確かめる |
| 主ユーザー | admin（運営者） |
| 達成したいこと | ①現状確認 ②文言修正 ③写真変更後の表示確認 |
| 最重要アクション | 文言を編集して「公開する」 |
| 情報の優先順位 | プレビュー（大きく） > 編集パネル > 端末幅切替 > 公開状態 |

## 3. 画面構成（UX設計）

`/admin/preview` に新設。**左=編集パネル / 右=ライブプレビュー** の2ペイン構成。

```
┌─ 画面タブ: [メイト選択] [メイト詳細] [プラン選択] [完了画面] ─────────┐
│ ┌─編集パネル(左・約360px)─┐ ┌─プレビュー(右・残り全幅)──────────┐ │
│ │ ▼ 見出し・案内文          │ │  幅: [スマホ375] [タブレット768] [PC] │ │
│ │  [トライアル案内 見出し]  │ │ ┌──────────────────────┐ │ │
│ │  [トライアル案内 本文]    │ │ │                            │ │ │
│ │ ▼ 空状態・エラー文言      │ │ │   実ページを iframe 表示     │ │ │
│ │  […]                     │ │ │   （本物のメイト写真・価格）  │ │ │
│ │ ▼ ボタン・バッジ          │ │ │                            │ │ │
│ │  […]                     │ │ └──────────────────────┘ │ │
│ └─────────────────┘ │  ↻ 再読み込み   ⧉ 新しいタブで開く    │ │
│ [⚠ 未保存の変更があります──[破棄] [下書き保存] [公開する]]（固定バー）│
└──────────────────────────────────────────────┘
```

### プレビュー（右ペイン）

- **実ページを iframe で表示**する（コピー画面を別実装しない）。データもレイアウトも本物なので、
  「プレビューでは合っていたのに本番で違う」が構造的に起きない
- 表示URL: `/subscribe/cast?preview=1` 等。`preview=1` のとき:
  - 下書き文言があれば下書きを表示（公開前の確認）
  - 「LINEからアクセスしてください」バナーは実際の見え方確認のため**そのまま表示**（隠さない）
- **幅切替**: スマホ(375) / タブレット(768) / PC。iframe の幅を変えるだけで実機相当の確認ができる
- **メイト詳細タブ**: メイト選択ドロップダウン付き。`?cast=<id>` で詳細モーダルを自動で開き、
  **写真変更後の確認**（並び・トリミング・1枚目サムネイル）をワンタップで行える
- **プラン選択タブ**: プレビュー対象メイトを選ぶ（価格はメイト別オーバーライドがあるため）
- **完了画面タブ**: 実画面はStripeの決済セッション必須のため、`preview=1` のときだけ
  **サンプル値（プラン・金額・トライアル日数）でモック表示**する分岐を画面側に追加
- 各タブに「新しいタブで開く」を併設（iframeでは確認しづらいスクロール感・LINE内ブラウザ相当の確認用）

### 文言編集（左ペイン）

- 編集対象の文言を**画面タブごとに、画面上の登場順**でグルーピング表示
  （「ファイル別」「キー名別」のような開発者の分類にしない）
- 各項目: ラベル（業務語。例「トライアル案内の見出し」）+ テキスト入力 + 文字数カウンタ
- `${days}`（トライアル日数）のような**差し込み変数はチップ表示**し、「この部分は自動で日数が入ります」
  と説明を添える。変数を消してしまった場合は保存前に警告
- 編集は**下書き保存 → プレビューで確認 → 公開** の2段階（本番文言を直接いじって
  タイポが即ユーザーに見える事故を防ぐ）
- **「編集して保存する」4点セット**を実装（グローバルルール準拠）:
  1. dirty tracking（初期値スナップショット比較）
  2. 画面下部固定の保存バー（スクロール位置に依存しない）
  3. 離脱ガード（beforeunload）
  4. 「破棄」で初期値へ復元
- 「初期値に戻す」を項目ごとに用意（DB行を消してコード内デフォルトへフォールバック）

### 写真確認の導線

- メイト詳細タブに「この伴走メイトの写真を編集」ボタン → `/admin/staff/[id]/photos` へ
- 写真編集から戻ったら ↻ 再読み込みで反映確認（force-dynamic なのでキャッシュ滞留なし）

## 4. データモデル

```sql
create table public.funnel_copy (
  key             text primary key,      -- 例 'cast.hero.title'
  draft_value     text null,             -- 下書き（プレビューのみで使用）
  published_value text null,             -- 公開値（null = コード内デフォルトを使用）
  updated_by      uuid references staff_profiles(id),
  updated_at      timestamptz not null default now()
);
-- RLS: SELECT/UPSERT = admin のみ（エンドユーザー画面は service_role 経由で published のみ読む）
```

**フォールバック連鎖**（`plan_prices` の resolvePlanPricing と同じ型）:
`published_value ?? コード内デフォルト`。プレビュー時のみ `draft_value ?? published_value ?? デフォルト`。
行が無くても壊れない＝**データ移行なしで即リリースできる**。

文言の取得は `getFunnelCopy(keys[])` を共有ヘルパー1つに集約し、各画面が同じ関数を使う。

## 5. 編集対象の文言（推奨スコープ = 第1弾）

**価値が高く、かつロジックに影響しない文言に限定**する（約25キー）:

| 画面 | 対象 |
|---|---|
| メイト選択 | ヒーロー見出し・本文 / ナビタイトル / 空状態2種 / LINE案内バナー見出し・本文 / 決済キャンセル文言 |
| メイト詳細 | CTA「この伴走メイトでプランを見る」 / プロフィール未設定時の文言 / 残り枠バッジの表示しきい値(数値) |
| プラン選択 | プラン名・説明文・SLA表示ラベル（3プラン分）/ おすすめバッジの対象プラン / 月額・年額トグルの注記 |
| 完了画面 | 見出し・本文（トライアル/年額/ライトの3分岐）/ LINE戻り案内 |

### 5b. LINE側の文言（第1弾に含める・ユーザー確定）

| 対象 | 内容 |
|---|---|
| welcomeメッセージ | 友だち追加時の挨拶文（`{days}`・`{subscribeUrl}` 変数入り） |
| 申込案内Flexカード | 通知文(altText)・見出し・本文・有効期限の注記・**ボタンラベル** |

**ボタンラベル問題の解法**: ボタンはタップするとラベル文字列がメッセージとして送信され、
webhookがその文字列でコマンド判定している。ラベルだけ編集すると**ボタンが反応しなくなる**ため、
webhook側の判定を「固定キーワード集合 ∪ 現在公開中のボタンラベル」に変更する。
これにより**どんなラベルに変えてもボタンは必ず動く**（旧ラベルのリッチメニューも動き続ける）。

**LINEプレビュー**: iframeは使えないため、①管理画面内にLINE風のトーク画面モック
（吹き出し・Flexカードの見た目再現）で下書きを表示 ②「テスト送信」ボタンで
運営の通知先LINE（新規会員通知と同じ宛先）へ実際に送って実機確認、の2段構え。

**第1弾で対象外とするもの（理由つき）**:

- **チェックアウトエラー文言** — エラー分類が文言の部分一致で行われており
  （`subscribe-checkout-errors.ts`）、編集すると分類が静かに壊れる。分類ロジックの
  コード化とセットでないと編集可能にできない
- **トライアル日数** — 環境変数かつStripeの請求設定と連動する事業数値。文言編集の範囲外
- **aria-label等の支援技術用文言** — 編集ミスのリスクに対して価値が低い
- **Flexカードの色** — 文言editorの範囲外（ブランドカラーはコード管理）

**変数の保護**: デフォルト文言に含まれる変数（`{days}`・`{subscribeUrl}`・`{price}` 等）が
編集後の文言から消えている場合は**保存をブロック**し、「この文言には {days} を含める必要があります」
と表示する（リンク切れ・情報欠落の事故を防ぐ）。

## 6. 前提リファクタ（実装前に必須）

同じ文言がコード内に複数実在するため、先に一本化しないと「編集したのに一部だけ変わらない」になる:

1. プラン名・説明・SLAラベル: `plan/page.tsx` と `lib/plan-pricing.ts` の二重定義 → 後者に統一
2. 性別ラベルマップ: 3箇所 → 共有定数に統一
3. `formatYen`: 3箇所 → 共有ヘルパーに統一
4. ナビタイトル「伴走メイトを選ぶ」: ページとスケルトンの2箇所 → 共有定数
   （スケルトンは同期表示のため定数参照。DB文言とズレる場合があるが一瞬のプレースホルダなので許容）

## 7. セキュリティ

- **iframe許可は `/subscribe/:path*` のみ**に限定して `frame-ancestors 'self'` へ緩和
  （X-Frame-Options はこのパスだけ外す。DENYは同一オリジンの埋め込みも拒否するため）。
  他の全ルートは現行の DENY / 'none' を維持。第三者サイトからのフレーミングは
  'self'（同一オリジン限定）なので引き続き不可＝クリックジャッキング耐性は実質変わらない
- `funnel_copy` の書き込みは admin のみ（RLS + Server Action の requireAdmin 二重）
- 文言はテキストとして描画（HTMLとして解釈しない）。XSSの持ち込み口にしない

## 8. エラー・空・ローディング

- プレビューiframeのロード中はスケルトン + 「プレビューを読み込んでいます…」
- iframe読み込み失敗時: 「プレビューを表示できませんでした。再読み込みしてください」+ 再試行ボタン
- 下書き保存失敗: 入力保持 + 原因と対処のトースト
- 公開の確認モーダル: 「公開すると、いま申込中のユーザーにも即時反映されます」

## 9. 権限・モバイル

- **admin のみ**（サイドナビ表示も admin 限定）※supervisorへの開放は要確認事項
- 管理者の主端末はPC想定だが、モバイル(375px)では**上下スタック**
  （プレビュー上・編集パネル下・保存バーはボトム固定）で崩れないこと

## 10. 実装フェーズ

| フェーズ | 内容 |
|---|---|
| P0 前提リファクタ | 重複文言の一本化（§6） |
| P1 基盤 | funnel_copy テーブル + getFunnelCopy + 画面側の差し替え（表示は現状と同一） |
| P2 プレビュー | ヘッダ緩和(/subscribe限定) + /admin/preview の閲覧機能（タブ・幅切替・cast深リンク・完了モック） |
| P3 編集 | 編集パネル + 下書き/公開 + 4点セット + 変数チップ |
| P4 検証 | 全幅(375/768/1280)実測 + 編集→下書き→公開→実画面反映のE2E手動確認 |

## 11. 要確認事項（設計の分岐）

1. **編集範囲**: 第1弾は上記25キー（web申込ファネルのみ・LINE文言は第2弾）でよいか
2. **公開フロー**: 「下書き→公開」の2段階でよいか（即時公開のほうが手数は少ないが事故リスクあり）
3. **権限**: admin のみでよいか、supervisor にも開放するか
