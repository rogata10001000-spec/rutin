# 要件: 1人で130人に伴走する体制（シナリオC）— 2026-10-14

GPT の事業評価（2026-10）を受けた再設計の要件。決定事項と実装順を固定するための文書。

## 0. 決定事項（2026-10-14・緒方）

| 項目 | 決定 |
|---|---|
| 事業ゴール | 手残り（運営の実質利益）**月100万円**。MRR は手段 |
| 自分の担当 | **自分で担当する利用者を段階的に 70 → 130 人**へ（取り分100%） |
| メイト | 3人 × 60人程度。配分は **70% → 60%** へ変更（配分ルール画面で設定。コード変更なし） |
| 卒業 | **卒業させない**。目標を達成したら／3か月経ったら**次の目標を設定**してもらい、同じメイトと継続する（複数メイト契約は別のアップセル） |
| 実装順 | ①検証指標（KPI） → ②構造化チェックイン → ③対応キュー → ④申込時の目標登録 → ⑤文言（3か月の型・次の目標） |

### 手残り100万の成立条件（試算）
- 自分 130人 × ARPU 6,800円 ≒ 88万、メイト 3人×60人×6,000円＝108万（60%配分 → 運営43万）、MRR ≒ 196万
- 控除: Stripe 4.3%（8.4万）・LINE 従量 3円/通（1.8万）・広告（解約8%→新規25人/月×CAC4,000円＝10万）・ツール3万 → **手残り ≒ 108万**
- **自分の担当1人はメイト担当の約3.3人分**の価値がある。よって本要件の中心は「自分が130人を1日3.5時間以内で回せること」。
- 成立条件: **返信1件の実作業時間 中央値 90秒以下**（130人×1日1返信×90秒＝3.3時間）。現状想定の3分では6.5時間で破綻する。

## 1. 既にあるもの（作らない）
- AI返信案の生成（手動・一括・**受信時の事前生成** `pregenerateDraftsForInbound`）と**採用追跡**（`ai_drafts.selected_at / sent_message_id / sent_body`）
- 返信SLA計測（`response_metrics`）、SLA警告cron、日次サマリー
- リスク検知（`risk_flags`。AI下書き生成時に判定）
- チェックインの**受信**（postback → `checkins` に ◯△× を保存）。※**送信側（催促Flex）は呼び出し元が無く未稼働**
- 日次集計（`daily_metrics`: follow/trial/subscribe/plan_change/cancel 等 ＋ active_users スナップショット）、ライフサイクルイベント（`subscription_lifecycle_events`。解約理由は metadata.cancel_reason_code）
- 売上・コホート・ファネル・マーケ（推定MRR）・AI利用状況の各画面
- 受信トレイの優先度・未返信フィルタ・一括送信・予約送信・テンプレ・メモ・ショートカット

## 2. フェーズ①: 検証指標（KPI）

### 2-1. 画面
- `/admin/kpi`（admin・supervisor）。**P0 → P1 → P2 の順に上から**並べ、各指標に「現在値・目標・状態（達成/注意/未達/データ不足）」を1行で出す。説明文は置かない（数字と色で分かる）。
- 管理ダッシュボード上部に **P0 の要約1行**（有料契約数・MRR・運営粗利・月次解約率）を置き、KPI 画面へリンク。
- 目標値は `lib/kpi-targets.ts` に1箇所（画面と通知で共有。Pull-Only Monitoring を避ける）。

### 2-2. 指標定義
**P0（事業が成立するか）**
| 指標 | 定義 | 目標 |
|---|---|---|
| 有料契約数 | `end_users.status in (active, past_due)` | — |
| MRR | 有料契約の月額合計（年額は /12。メイト別価格を考慮） | — |
| ARPU | MRR / 有料契約数 | — |
| 運営粗利（推定） | MRR − メイト配分（配分ルール。自分の担当は0%） − Stripe 4.3% − LINE 3円×有料×30通 | **月100万** |
| 自分の担当人数 | `assigned_cast_id` が運営担当者（下記2-4）の有料契約数 | 130 |
| トライアル→有料転換率 | 過去60日に `trial_start` し、トライアル終了日を過ぎた人のうち `subscribe` に至った割合 | **30%以上** |
| 30日継続率 | 30〜60日前に有料開始（`subscribed_at`）した人のうち、30日後時点で解約していない割合 | **80%以上** |
| 月次解約率 | 直近30日の `cancel`（確定）数 ÷ 30日前の有料契約数 | **8%以下** |

**P1（1人で回っているか）**
| 指標 | 定義 | 目標 |
|---|---|---|
| 返信1件の実作業時間 | 会話を開いてから送信までの秒数（新規 `messages.handling_seconds`、クライアント計測）。直近7日の中央値・担当者別 | **90秒以下** |
| 1日の返信件数・総対応時間 | 担当者別・直近7日平均 | 130件 / 3.5時間以内 |
| AI下書き採用率 | 直近7日の事前生成/手動生成のうち `selected_at` あり。編集あり（`sent_body ≠ body`）/そのまま を分ける | 70%以上 |
| SLA遵守率 | `response_metrics.sla_breached=false` の割合（7日） | 95%以上 |
| 未返信（今日） | 既存の summary | 0 |

**P2（価値が出ているか）**
| 指標 | 定義 | 目標 |
|---|---|---|
| トライアル中の初回報告率 | トライアル開始から72時間以内に受信メッセージ or チェックインがある割合 | **80%以上** |
| 週あたり報告日数 | 有料利用者の直近7日の「受信 or チェックインがある日」の平均 | 4日以上 |
| 達成（◯）割合 | 直近30日の checkins のうち circle | 50%以上 |
| 目標達成・次の目標設定数 | フェーズ④以降（`end_user_goals` の completed / 新規） | — |
| 解約理由の分布 | `subscription_lifecycle_events(cancel_scheduled).metadata.cancel_reason_code` の30日集計 | — |
| 獲得元別の新規 | 既存ファネルの acquisition_source | — |

CAC は広告費の手入力が要るため**後続**（月次の広告費入力欄を作ってから）。

### 2-3. 通知
- 日次サマリー（運営LINE・22時）に **P0 の未達**を1行追加（1日1回 claim）。判定は画面と同じ `lib/kpi-targets.ts` を使う。データ不足（分母が10未満）は通知しない。

### 2-4. 「自分の担当」の表現
- 運営担当者＝ **role=admin のスタッフも担当者に割り当て可能**にする（担当変更ダイアログの候補に admin を含める。配分計算では admin 担当分の配分は 0%＝運営100%）。設定テーブルは増やさない。

## 3. フェーズ②: 構造化チェックイン
- 朝9時（JST）の cron で、`plans.daily_checkin_enabled` のプランの有料・トライアル利用者に**チェックイン催促 Flex**（◯△×ボタン。既存 `sendCheckinFlexMessage`）を送る。送信元はその人の会話アカウント。claim（`checkin_prompts(end_user_id, date)` unique）で多重発火を防ぐ。
- 回答（postback）は既存どおり `checkins` に保存し、**受信トレイの利用者カードに直近7日の ◯△× を表示**、AI下書きの文脈に含める。
- 回答時に短い**自動返信（reply token・無料）**を返す（「記録しました。今日の様子を一言教えてください」）。※この返信は人の返信の代わりではなく、報告のハードルを下げるための受け取り確認。
- 利用者が「報告が止まった」状態（2日チェックインも受信も無い）を**沈黙フラグ**として受信トレイの優先度に反映し、5日で個別フォローの下書きをキューに積む。
- LINE 通数: 催促は push（1通/人/日）。130人で月3,900通＝約1.2万円。許容。

## 4. フェーズ③: 対応キュー
- 受信トレイに「**今日の対応**」モード: 未返信 → 今日未送信 → 沈黙者 の順で1本の流れにし、開いた瞬間に**事前生成済みの下書き**（受信時生成＋朝のチェックイン回答後にも生成）が選択された状態で表示。**Enter/⌘Enter で送信して次へ**。生成待ちをゼロにする。
- 下書きの文脈: 目標（フェーズ④）、直近7日のチェックイン、直近の受信、メモ、口調設定。
- 受信の**自動仕分け**（報告／相談／雑談／危険サイン／解約兆候）を事前生成時に同時に判定して保存し、危険サイン・解約兆候はキューの先頭＋赤バッジ。
- 送信時に `handling_seconds` を保存（フェーズ①の指標）。
- モバイル（自分がスマホから返す前提）で親指だけで「承認→次へ」が回ること。

## 5. フェーズ④: 申込時の目標登録
- 新テーブル `end_user_goals(id, end_user_id, category, title, weekly_target, started_at, review_at, status: active|achieved|replaced, created_at)`。1人につき active は1件。
- 入力: 申込完了画面に3項目（カテゴリ選択・目標の一文・週の回数）。未入力なら LINE の初回案内で聞く。メイト側（受信トレイの利用者カード）からも編集可。
- 表示: 受信トレイの利用者カード・ユーザー詳細・AI下書きの文脈。
- 期日: `review_at`＝開始から90日。到達時に「目標の振り返り」をキューに積む（フェーズ⑤の型）。

## 6. フェーズ⑤: 文言（3か月の型・次の目標）
- 「3か月で自分で続けられる状態を目指し、できたら次の目標へ」を全接点で揃える。**卒業という語は使わない**。
  - 1か月目: まず始める／2か月目: 続けやすい型を作る／3か月目: 自分で続けられる日を増やす／4か月目〜: **次の目標を決める**（同じメイトと続ける）
- 入れる場所: プラン選択画面の上部案内、申込完了画面、ステップ配信（7・30・60・90日目の振り返り）、受信トレイの利用者カードの「ステージ」、解約フロー（「次の目標を設定する」「維持プラン（Light）に変更する」を解約の前に提示）。
- Light を「維持プラン（週1の振り返り）」として再定義。Premium は「週1の個別振り返り＋目標の見直し」を提供物として明記。
- 文言は申込ファネル文言（funnel_copy）の既存の仕組みに乗せ、管理画面から変えられるようにする。

## 7. 検証（各フェーズの完了条件）
- ①: KPI 画面が実データで描画され、閾値割れが運営LINEに届く（手動で閾値を下げて1回実測し、元に戻す）。`handling_seconds` が実送信で記録される。
- ②: 朝の催促が自分の LINE に届き、◯を押すと checkins に入り、受信トレイに表示される。2回連続実行で2回目が no-op。
- ③: 未返信3件を「承認→次へ」だけで送り切る実測（1件あたりの秒数を記録）。
- ④: 申込完了画面で目標を入れて保存→受信トレイで表示→AI下書きに反映。
- ⑤: 各接点の文言を実機スクショで確認。「卒業」が0件（grep）。
