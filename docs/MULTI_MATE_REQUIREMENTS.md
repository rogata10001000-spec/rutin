# 複数メイト契約（追加契約）要件

作成: 2026-08-17 / 目的: 既存契約者が **マイページから別のメイトを追加契約**できるようにし、1人あたりのLTVを最大化する。

---

## 1. 前提の再確認（なぜ今の設計では追加できないか）

現在のシステムは **「1ユーザー = 1メイト = 1ライブ契約」** で堅牢化されている（2026-07-07の意思決定）。
追加契約を塞いでいるのは以下の4層。すべて意図的に入れたもので、外すのではなく**単位を変える**。

| 層 | 実装 | 現在の効果 |
|----|------|-----------|
| 入口 | `actions/subscriptions.ts` の「既に契約中のプランがあります」 | 契約者は申込フローに入れない |
| 入口 | 新規チェックアウト作成時に前セッションを `expire` | 2つ目の決済ページを開けない |
| Webhook | `cancelIfDuplicateLiveSubscription` | 2つ目の契約が完了したら自動キャンセル＋運営通知 |
| DB | 部分ユニーク索引 `uq_subscriptions_live_per_user` | ライブ契約は1ユーザー1件 |

さらに識別子レベルの制約:

| 制約 | 内容 |
|------|------|
| `end_users.line_user_id` | **グローバルUNIQUE**（1 LINE UID = 1行） |
| `end_users.assigned_cast_id` | 担当メイトは1人（99箇所・24ファイルが参照） |
| `messages` | `end_user_id` のみでスレッド化（`line_account_id` は記録済みだが絞り込みに未使用） |

---

## 2. 設計判断: 「会員行 = 1つのメイトとの関係」（採用）

### 2.1 検討した2案

**案B: 会員1行のまま、`subscriptions` に `cast_id` を足して契約を複数持つ**
- `assigned_cast_id`（99箇所）の意味が壊れる。担当判定・受信トレイ・SLA・LINE送信元・配分がすべて分岐必要
- **メッセージ基盤（最も壊してはいけない層）を改造することになる**
- 却下

**案A: 会員行を「人 × メイト」の関係ごとに持ち、その上に「人（person）」を置く** ← **採用**
- LINE公式アカウントは**メイトごとに分かれている**（`line_official_accounts.cast_id`）。
  利用者にとって、メイトAとの会話とメイトBとの会話は**LINE上で物理的に別のトーク**である。
  会員行を関係ごとに持つのは、この現実に1対1で対応する。
- 既存コードの前提「1 end_user = 1メイト = 1契約」は**そのまま真のまま**になる。
  受信トレイ・SLA・担当判定・チェックイン・リスク・配分は**一切変更不要**。
- 追加するのは「人」レイヤーだけ。

### 2.2 採用モデル

```
persons                     … 人（LTV・トライアル権・ログインの単位）
  └─ end_users (person_id)  … その人の「あるメイトとの関係」= 1契約
       ├─ subscriptions     … 1ライブ契約（既存の索引がそのまま効く）
       ├─ messages          … そのメイトとのトーク
       └─ checkins / risk_flags / memos …
```

- **LTV・トライアル権・ログイン** = person 単位
- **契約・会話・SLA・担当** = end_users 単位（＝今までどおり）

## 3. 識別子の扱い（最重要）

### 3.1 LINE UID の一意制約を緩める

`end_users.line_user_id` のグローバルUNIQUEを、**メイトごとに1行**を許す部分ユニーク索引へ置き換える。

```sql
create unique index uq_end_users_line_uid_per_mate
  on end_users (line_user_id, coalesce(assigned_cast_id, '00000000-0000-0000-0000-000000000000'::uuid))
  where line_user_id is not null;
```

- 未契約の見込み行（`assigned_cast_id is null`）は **人につき1行**（`coalesce` で NULL を実値化。
  素の複合UNIQUEは NULL を互いに異なる値として扱うため、これが無いと見込み行が無限に増える）
- 契約済みはメイトごとに1行

### 3.2 LINEプロバイダーに関する前提（運用制約・要確認）

LINEの `userId` は**プロバイダー単位で同一**。したがって:

- **全メイトの公式アカウントが同一プロバイダー配下** → 同じ人は全メイトで同じUID。
  3.1の索引により同一UIDが複数行に入るため、この索引が**必須**。
- **プロバイダーが分かれている** → メイトごとにUIDが異なる。3.1の索引は現状と同じ挙動になり無害。

どちらでも壊れないよう3.1の形にする。ただし**同一プロバイダー運用を推奨**（人の紐付けがUIDで自動的に成立するため）。
プロバイダーが分かれる場合、追加契約した2人目のメイトのLINEを友だち追加しても
システムは同一人物と判定できないため、**管理画面からの手動紐付け**（4.6）が必要になる。

### 3.3 追加契約時の行の作り方

追加契約は**決済完了時**に2つ目の `end_users` 行を作る（決済前に作ると未払いの空行が溜まる）。

| タイミング | 動作 |
|-----------|------|
| マイページで「メイトBを追加」 | Stripe Checkout を作成。metadata に `person_id` / `cast_id` / `add_mate=true` |
| 決済完了（Webhook） | `person_id` の下に **メイトB用の end_users 行**を作成（`line_user_id` は既存UIDを流用）→ `subscriptions` を紐付け |
| メイトBのLINEを友だち追加 | Webhook が (UID, 受信OAのcast) で**その行**に着地する |

## 4. 機能要件

### 4.1 マイページ（`/account/plan`）

**現在**: 1契約のみ表示（`getMySubscription` が最新1件を `limit(1)` で取得）

**変更後**:
- その人の**すべてのライブ契約をカードで一覧**（メイト名・写真・プラン・状態・次回請求日）
- 各カードに従来の操作（プラン変更 / 一時停止 / 解約 / 再開 / 支払い方法）
- 一覧の末尾に **「別のメイトも追加する」** CTA
  - 契約可能なメイトが残っていない場合は非表示
  - 空状態（契約ゼロ）は従来どおり「メイトを選ぶ」

### 4.2 追加契約フロー

```
マイページ「別のメイトも追加する」
  → メイト選択（★契約済みメイトは除外。満員も除外）
  → プラン選択
  → Stripe Checkout
  → 完了画面（★「メイトBのLINEを友だち追加してください」を必ず表示）
```

- 既存の `/subscribe/cast` → `/subscribe/plan` を **`?mode=add` で再利用**する
  （画面を作り分けると[同一データの複数の出口]の不整合を生むため）
- 見出し・文言は mode で切り替える（「メイトを選ぶ」→「追加するメイトを選ぶ」）

### 4.3 ガード（多層防御）

| # | ガード | 層 | 内容 |
|---|--------|----|----|
| G1 | 同一メイトの重複契約 | 入口＋DB | 既にライブ契約のあるメイトは選択肢から除外＋サーバー検証。DBは `uq_subscriptions_live_per_user`（end_users行単位）が最終防衛線 |
| G2 | **トライアルの重複取得** | 入口 | トライアル権は **person 単位**。1人目でトライアル済みなら2人目以降は**トライアルなしで即課金**。ここを end_users 単位のままにすると「メイトを変えるたび無料」の穴になる |
| G3 | 同時決済レース | 入口 | チェックアウトセッションの失効は**関係行（end_users）単位**。メイトAの決済ページを開いたままメイトBを申し込んでも互いを失効させない |
| G4 | 二重契約の自動キャンセル | Webhook | **同一メイト**への2つ目だけを重複と判定する（別メイトは正当な追加契約なのでキャンセルしない） |
| G5 | メイトの受付枠 | 入口＋Webhook | 既存の `capacity_limit` 判定をそのまま使う |
| G6 | 上限 | 入口 | 1人あたりの同時契約メイト数の上限（既定3・設定可能）。青天井にしない |

### 4.4 LINE ルーティング

- 受信: `(line_user_id, 受信したOAのcast)` で関係行を解決する（`pickRelationshipRow`）。
  従来は `line_user_id` のみで引いていたため、2契約目があると**どちらの行に着地するか不定**だった。
- **`shouldRejectAsWrongMate` は削除した**。着地先を受信OAのメイトで解決するようになった結果、
  メイトB宛のメッセージがメイトAのトークへ混ざることは構造的に起きなくなり、この判定は
  常に false を返す到達不能コードになったため。
- 別メイトと契約中の人が**未契約メイト**へ連絡してきた場合は、弾かずに
  「そのメイトを追加契約できます」と案内する（`replyAddMateGuide`）。追加契約の機会にする。
- 送信: 従来どおり関係行の `primary_line_account_id` / 担当メイトのOA。

### 4.5 通知・案内

- 追加契約時の運営通知に「**追加契約（2人目）**」と明記（新規獲得と区別して数えられるように）
- 完了画面・LINE通知に**メイトBの友だち追加URL**を必ず出す（[外部チャネルで送るリンク]の章に従い、
  認証必須ページへは飛ばさない）

### 4.6 管理画面

- ユーザー詳細に **「同じ人の他の契約」** セクション（メイト名・プラン・状態・リンク）… **実装済み**
- ユーザー一覧の**人物バッジ**… **未実装**（詳細画面で取り違えは防げるため後回し）
- **手動での人物紐付け**… DB関数 `link_end_user_persons` のみ実装、**UIは未実装**。
  全メイトのLINE公式アカウントが同一プロバイダー配下なら同じ人のUIDは共通のため不要。
  プロバイダーが分かれている運用に変えるときに作る

### 4.7 分析・LTV（実装済み）

マーケティング画面に「1人あたりの状況（複数メイト契約）」セクションを追加した。

- **実人数** / **複数メイト率**（＝この施策のKPI）/ **1人あたりARPU** / **1人あたりLTV近似** / 平均契約メイト数
- 既存の ARPU・LTV は母数が契約数なので **「1契約あたり」と明記**した。
  複数メイト対応後は契約数 ≠ 人数になり、ラベルを変えないと
  追加契約が増えるほど「1人あたりの支払い」が実態より小さく見える（指標の意味が黙って変わる）
- 算出は `lib/person-metrics.ts` の純関数に集約し単体テスト5件で固定

## 6. 実装順序

1. **DB**: `persons`・`person_id`・索引張り替え・backfill（既存1件は1人1契約なので安全）
2. **解決層**: `lib/person.ts` / `lib/relationship-routing.ts` ＋ 単体テスト
3. **Webhook（LINE）**: 関係行の解決を差し替え（既存1契約の挙動が変わらないこと）
4. **申込**: 追加契約モード・トライアル権 person 単位・セッション失効の単位修正
5. **Webhook（Stripe）**: 追加契約の行作成・重複判定のメイト単位化
6. **マイページ**: 複数契約表示＋追加CTA
7. **管理画面・分析**
8. 検証（型・ビルド・テスト・実測）

## 7. 検証項目（2026-08-17 実施）

検証で作成したデータはすべて削除し、`end_users` 1件 / `subscriptions` 2件 / `persons` 1件 の
元の状態に復元済み（実測で確認）。

| # | 項目 | 結果 | 検証方法 |
|---|------|------|---------|
| 1 | 既存の1契約ユーザーの挙動が変わらない | ✅ | 実画面。マイページは従来どおり1枚のカードで表示され、アコーディオンにならない。プラン変更・解約の導線も同じ |
| 2 | 追加契約でメイトBの行が作られ、メイトAの会話に混ざらない | ✅ | 実DB。同一UID・同一person・別メイトの行を作成し、`messages` が関係行ごとに分離することを確認 |
| 3 | 2人目に**トライアルが付かない** | ✅ | 実画面。`/subscribe/plan?mode=add` が「お申し込み後すぐに…請求されます」となりCTAも「このプランで申し込む」。トライアル権は person 単位で判定 |
| 4 | 同一メイトの重複契約が入口・DB両方で弾かれる | ✅ | 入口=`canContractWithCast`（単体テスト）／DB=`uq_end_users_person_cast` が 23505 で拒否（実測） |
| 5 | メイトAの決済ページを開いたままメイトBを申し込んでも互いを失効させない | ✅ | セッション失効を関係行（`end_users.id`）単位に限定。コードレビュー＋型検査 |
| 6 | メイトBのLINE受信がメイトBの行に着地する | ✅ | `pickRelationshipRow` の単体テスト（11件）。受信アカウントのメイトで解決 |
| 7 | 解約後に同じメイトを再契約できる | ✅ | `getLiveContractedCastIds` はライブ状態のみを返すため、解約済みメイトは候補に残る（単体テスト） |
| 8 | 契約可能なメイトがゼロなら追加CTAが出ない | ✅ | 実画面。2メイトとも契約中のとき「いま新しく受付できるメイトがいないため…」を表示しCTAは非表示 |
| 9 | 追加契約が二重契約として自動キャンセルされない | ✅ | Stripe Webhook の単体テストで固定（別メイトはキャンセルされず行が作られる） |
| 10 | 375px / 768px で横溢しない | ✅ | 実測 `scrollWidth - clientWidth = 0` |

**補足（実装済みだが実データでの発火は未確認）**: 追加契約完了画面の「メイトBを友だち追加」導線は、
実際のStripe決済を伴うため本番決済を避けて未通し。ロジックは
「同一personのライブ契約が2件以上のときに表示」で、その判定材料（`getLiveContractedCastIds`）は実測済み。
